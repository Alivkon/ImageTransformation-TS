!Резюме

План концептуально зрелый: верно выбрана архитектура «один контейнер + host-маршрутизация», честно зафиксирована SEO-цена отказа от старого домена, есть критерии готовности и порядок выкладки. Однако план написан без глубокой сверки с кодовой базой и фактической инфраструктурой. Самые опасные расхождения:

  • Traefik сконфигурирован в двух местах, и план упоминает только одно — риск изменить не то место (крит. №1);
  • исторические абсолютные URL в БД и сообщениях Telegram не имеют плана миграции (крит. №2);
  • часть чеклиста основана на несуществующем коде — return_url у ЮKassa (сущ. №5).

Каждый недочёт ниже привязан к конкретному файлу и строкам проекта. Итоговая карта соответствия — в разделе «Пункт плана ↔ код», приоритезированные правки — в разделе «Рекомендации».

Критические · 3 Критические недочёты — план не знает реальную инфраструктуру

1В проекте два источника конфигурации Traefik, и план упоминает только один

Раздел 4 плана говорит: «В docker-compose.yml заменить router старого домена». Фактически конфигурация разбита на два независимых места:

  • docker-compose.yml, строки 51–57 — labels-роутер imagetransformation;
  • deploy/traefik/dynamic/imagetransformation.yml — file-provider: роутеры imagetransformation и imagetransformation-www с middleware redirect-to-apex.

При этом Traefik из deploy/traefik/docker-compose.yml не монтирует docker.sock и не включает docker-провайдер (в command только --providers.file.directory) — значит, labels из compose-файла бота он не читает вовсе, а рабочим источником является YAML. Возможно наличие второго общего Traefik (бот подключён к внешней сети n8n_default, где может работать другой прокси).

Риск при исполнении: исполнитель изменит не то место — старый домен останется живым в другом провайдере. Критерий «удалить imagetransformation.ru из router» будет формально выполнен, а трафик пойдёт по старой схеме. Плану нужна инвентаризация: где терминируется TLS и какой провайдер активен.

2Исторические данные со старым доменом: план миграции нет

В src/web/generateRoute.ts (строка 86):

const publicImageUrl = `${WEBAPP_URL}${uploadUrl}`;

Абсолютные URL результатов генераций сохраняются в БД (история) и уходят в сообщения Telegram. После шага 13 («удалить imagetransformation.ru из DNS») все ранее выданные ссылки отвалятся — включая ссылки на оплаченные генерации пользователей.

В плане отсутствуют: резервная копия Postgres перед миграцией, UPDATE-скрипт перезаписи домена в сохранённых URL либо переходный период, когда старый домен продолжает раздавать только /uploads/. Критерий №7 («grep по коду не находит домен») покрывает код, но не данные.

Риск: жалобы платных пользователей на «пропавшие» результаты сразу после переключения; откат затруднён без бэкапа БД.

3Неподтверждённые регистрации умрут в момент переключения

src/email.ts, строка 12: ссылка подтверждения строится из WEBAPP_URL; токены живут 24 часа (текст письма зашит там же). Все письма, отправленные до деплоя новой версии, содержат старый домен — после его отключения часть свежих регистраций не сможет подтвердить email.

Что добавить в план: выбрать окно миграции вне пиковой регистрации и/или временно оставить на старом домене раздачу /api/auth/verify до истечения выданных токенов.

Существенные · 7 Существенные недочёты планирования

4Судьба старых путей на новом основном домене не определена

Страницы уже индексируются по URL вида https://imagetransformation.ru/uluchshit-gruppovoe-foto. В целевой схеме эти пути на новом основном домене просто исчезают. Отказ от 301 со старого домена зафиксирован как бизнес-решение (раздел 5) — но план молчит о путях на новом домене. Минимум: постоянные 301 с portret-iz-foto-ai.ru/<старая-страница> на корень соответствующего нового домена. Это бесплатно, сохраняет внутренние переходы и часть SEO. Без этого теряется весь накопленный трафик семи посадочных.

5Чеклист ЮKassa основан на несуществующем коде

В src/services/yookassa.ts платёж создаётся с confirmation: { type: "embedded" } (строка 47) — параметра return_url в коде нет вовсе. Пункт плана «проверить return_url успешной оплаты» (раздел 8) вводит исполнителя в заблуждение: реально нужно тестировать виджет на pay_yookassa.html и confirm-флоу /api/payments/confirm после смены домена.

6Динамические robots.txt/sitemap.xml конфликтуют со статической раздачей

Оба файла — физические файлы в static/, которые раздаёт @fastify/static (src/webServer.ts, строка 109). Требование «свой robots.txt на каждом домене» требует явных маршрутов поверх статики и исключения файлов из раздачи — плагин не умеет exclude-листы. То же с закрытием /site/*.html: файлы должны остаться на диске (sendFile их читает), но перестать публиковаться — нужна реорганизация каталогов (приватный каталог вне корня статики), которую план не проектирует.

Следствие: без реорганизации на любом домене остаются прямые ссылки /admin.html, /pay_yookassa.html, /privacy.html, верификационные файлы Bing/Яндекс — требование «служебное только на основном домене» не выполняется.

7Не определено, кто отвечает на неизвестный домен

Если для домена нет роутера, запрос не дойдёт до Fastify — Traefik сам вернёт 404. Требование «неизвестный домен получает 421/404 от приложения» достижимо только через catch-all роутер в Traefik. Кроме того, для надёжного разбора Host за прокси нужны trustProxy в Fastify и учёт x-forwarded-host/порта в Host. Ни то, ни другое в плане не упомянуто.

8Локальная разработка и ngrok сломаются

После host-маршрутизации запросы с localhost:8080 попадут в категорию «неизвестный домен». В коде остались хедеры ngrok-skip-browser-warning (src/webServer.ts) — привычный сценарий демо через ngrok тоже отвалится. Нужен dev-fallback в конфиге доменов (например, localhost/127.0.0.1/DEV_HOST → главная страница). В плане этого нет — сломается yarn dev и процесс отладки.

9BCC писем указывает на посторонний домен

src/email.ts, строка 16: bcc: "hello@ritual-retouch.ru". План пишет абстрактно «проверить BCC», хотя факт таков: скрытая копия уходит на домен, которого нет ни в плане, ни в целевой схеме. После смены SMTP_FROM на новый домен несогласованность SPF/DKIM/DMARC повышает риск попадания в спам — обязательны реальные тесты доставки письма подтверждения, а не галочка «проверено».

10«Централизованный конфиг доменов» нереализуем для HTML в предложенном виде

Конфиг в TS полезен для src/config.ts:41, src/keyboards/inline.ts:14,34, src/email.ts:12, src/handlers/start.ts:26, src/web/generateRoute.ts:86. Но домены зашиты и в статичный HTML — canonical, JSON-LD, CTA, по 3–6 вхождений в каждом файле static/site/*.html. Без шаблонизации или генерации HTML дублирование останется. План не выбирает механизм — при исполнении возникнет импровизация.

Средние · 9 Средние недочёты

  • 11. Верификационные файлы старых вебмастеров. В static/ лежат «BingSiteAuth .xml» (с пробелом в имени!) и yandex_af11eab875ed4358.html — артефакты старого домена. Для шести новых доменов нужны шесть новых комплектов; их публикация на новых хостах планом не описана.
  • 12. frontend/public/robots.txt не упомянут. Vite копирует его в frontend-dist → /app/robots.txt; там тоже может быть старый домен, и критерий «grep не находит домен» провалится.
  • 13. Артефакты репозитория. Корневой index.html (24 КБ), INTERNATIONAL_SITE_MIGRATION_PLAN.md, а также непересобранные dist/ и frontend-dist/ содержат старый домен и провалят чеклист «поиск по репозиторию».
  • 14. Метрика. Код счётчика 111270321 продублирован в каждом HTML; при выборе «один счётчик на все домены» нужно разрешить эти домены в настройках счётчика, иначе визиты не будут считаться. Выбор схемы сознательно отложен — риск потери статистики в переходный период.
  • 15. Атрибуция landing_domain — это новая фича (изменения схемы БД + логика регистрации), а не настройка; объём работ в плане не оценён.
  • 16. Let's Encrypt. Шесть новых сертификатов TLS-challenge — в пределах лимитов, но многократные пересоздания упрутся в duplicate-cert лимит (5/нед.). Нужна обкатка на staging-resolver.
  • 17. www оставлен как развилка («либо не создаются, либо редирект»). Для 6 доменов это 12 вариантов решения; определиться нужно до покупки DNS (в старом конфиге www был с редиректом — прецедент есть).
  • 18. Точки невозврата нет. Откат описан только для образа приложения; после удаления DNS (шаг 13) откат невозможен в принципе. Точку невозврата нужно назвать явно.
  • 19. Бэкап БД не предусмотрен вообще (только .env/Traefik) — обязателен при любом сценарии с перезаписью URL (см. крит. №2).

Мелкие · 6 Мелкие замечания — всплывут при исполнении

  • 20. Бренд. Тема письма и заголовки страниц содержат имя «ImageTransformation»; план меняет домен, но не решает вопрос нейминга и реквизитов — оферту и политику надо вычитывать целиком, а не менять только e-mail и «адрес сайта».
  • 21. Sitemap основного домена: перечень «выбранных информационных страниц» не определён; после переезда пяти страниц их надо исключить из sitemap основного домена, иначе ссылки на несуществующие пути.
  • 22. og:image: абсолютный URL с какого домена — не решено. Связано с кросс-доменной статикой: CSS/favicon с основного домена = cross-origin запросы и единая точка отказа для пяти лендингов.
  • 23. Автотестов нет (package.json без test-скрипта); для матрицы «6 доменов × ~10 путей» стоит положить в репозиторий curl-smoke скрипт вместо ручного прогона.
  • 24. Мониторинг: «несколько дней контролировать ошибки» ничем не обеспечено — ни алертов, ни uptime-проверок по шести доменам.
  • 25. Регистрация пяти новых доменов в плане не упомянута (предполагаются купленными и делегированными) — если это не так, всплывёт в последний момент.

Плюсы Что план делает хорошо

  • Честно зафиксирована SEO-цена отказа от старого домена (раздел 5) — это осознанное бизнес-решение, а не скрытая ошибка миграции.
  • Правильная архитектура: один контейнер и host-маршрутизация вместо шести экземпляров приложения.
  • Замечена проблема дублей /site/*.html; выбран корректный статус 308 для редиректа /app.
  • Внимание к IP-whitelist вебхука ЮKassa и верное решение не трогать Vite base: "/app/".
  • Есть критерии готовности, порядок выкладки и раздел отката — каркас хороший, требует лишь сверки с кодом.

Правки Рекомендуемые правки DOMAIN_MIGRATION_PLAN.md (по приоритету)

  1. P0 — Инвентаризация Traefik. Определить активный провайдер (labels vs file-provider), где терминируется TLS; зафиксировать единственный источник правды, обновить оба места либо удалить мёртвое. Без этого шаг 4 плана непредсказуем.
  2. P0 — Новый раздел «Миграция данных». pg_dump перед началом; стратегия для исторических URL: UPDATE-скрипт по сохранённым ссылкам генераций либо переходный период, когда старый домен раздаёт только /uploads/ и /api/auth/verify.
  3. P0 — Судьба старых путей. Постоянные 301 с portret-iz-foto-ai.ru/<старая-страница> на корни новых доменов; зафиксировать в разделе маршрутизации.
  4. P1 — Структура каталогов. Приватный каталог для HTML вне корня статической раздачи; явные маршруты robots.txt/sitemap.xml поверх статики; запрет прямых /site/*, /admin.html, /pay_yookassa.html на тематических доменах.
  5. P1 — Unknown host и www. Catch-all роутер в Traefik + trustProxy; выбрать код ответа (421/404); единое решение по www для всех шести доменов до покупки DNS.
  6. P1 — Dev-fallback. localhost/127.0.0.1/DEV_HOST → главная страница, чтобы не сломать yarn dev и ngrok-демо.
  7. P1 — Корректировка чеклиста ЮKassa и почты. Заменить пункт про return_url тестом виджета и confirm-флоу; добавить обязательный тест доставки письма с новым SMTP_FROM/BCC (учесть ritual-retouch.ru).
  8. P2 — Чеклист чистоты дополнить: frontend/public/robots.txt, корневой index.html, INTERNATIONAL_SITE_MIGRATION_PLAN.md, пересборка dist//frontend-dist/, верификационные файлы Bing/Яндекс, .env.example.
  9. P2 — Откат. Добавить pg_dump в состав бэкапов; явно назвать точку невозврата (удаление DNS старого домена) и порядок возврата внешних интеграций при откате.
  10. P2 — Тестирование и мониторинг. curl-smoke скрипт «домен × путь» в репозиторий; uptime-проверки шести доменов и алерты на первые дни после переключения; обкатка сертификатов на staging-resolver Let's Encrypt.
  11. P2 — Аналитика. Выбрать схему Метрики (один счётчик vs раздельные) и оценить как фичу сохранение landing_domain/UTM при регистрации.
