# План реализации перехода на новые домены

Рабочий документ: решения фиксируются последовательно, по итогам опроса.
Базовый план: `DOMAIN_MIGRATION_PLAN.md`. Ревизия рисков: `PLAN_REVIEW_REPORT.html`.

## Целевая схема (зафиксировано)

Один контейнер Fastify (:8080) обслуживает все шесть доменов, маршрутизация по заголовку `Host`:

| Домен | Что отдаёт |
|---|---|
| `portret-iz-foto-ai.ru` | Приложение, SPA `/app/`, API, uploads, юридику, админку, оплату |
| `raskrasitfoto-ai.ru` | `site/raskrasit-cherno-beloe-foto.html` |
| `restavraciyafoto-ai.ru` | `site/restavraciya-staryh-foto.html` |
| `semeynoe-foto-ai.ru` | `site/zhivopisnyy-portret-kak-podarok-na-yubiley.html` |
| `gruppovoe-foto.ru` | `site/uluchshit-gruppovoe-foto.html` |
| `delovoy-portret-ai.ru` | `site/delovoy-portret-iz-foto.html` |

### Решение 1 (P0). Инвентаризация Traefik — выполнить ДО любых правок

**Ответ владельца:** точная рабочая конфигурация неизвестна → первым шагом плана идёт инвентаризация на сервере.

**Шаги инвентаризации:**
1. `docker ps --format '{{.Names}} {{.Image}}' | grep -i traefik` — найти все Traefik-инстансы (возможен общий для n8n).
2. Для каждого: `docker inspect <name> --format '{{json .Mounts}} {{json .Args}}'` — есть ли docker.sock, включён ли docker-провайдер, какой `--providers.file.directory`.
3. Через API активного Traefik выгрузить фактические роутеры: `curl -s http://127.0.0.1:<api-port>/api/http/routers | jq '.[] | select(.service | test("imagetransformation"))'`.
4. Установить источник живого роутера `imagetransformation`: labels бота или `deploy/traefik/dynamic/imagetransformation.yml`.
5. Сверить `acme.json` активного Traefik — какие сертификаты реально выданы.

**Критерий завершения:** однозначно определён единственный рабочий источник конфигурации — только в него добавляются роутеры шести новых доменов; мёртвый дубликат помечается к удалению на этапе чистки.
**Правило переходного периода:** до завершения инвентаризации ничего не менять ни в labels, ни в dynamic/*.yml.

> **✅ ИТОГ ИНВЕНТАРИЗАЦИИ (22.08.2026, детали в EXECUTION_LOG.md):** на сервере один Traefik — контейнер **`n8n-traefik-1`**; docker-провайдер у него выключен, все живые роутеры `@file`. Рабочий источник = каталог **`/opt/traefik-dynamic/*.yml`** (права root, правки через sudo). Labels в `docker-compose.yml` бота мертвы → удаляются при чистке. Новые роутеры шести доменов кладём отдельным файлом `/opt/traefik-dynamic/portret-domains.yml`; старый `imagetransformation.yml` удаляется на шаге 5 вечера D0.

### Решение 2 (P0). Исторические ссылки на сгенерированные фото

**Ответ владельца:** ничего не делать — старые ссылки считаются утраченными.

**Зафиксировано:**
- UPDATE-скрипт перезаписи домена в БД **не выполняется**;
- переходная раздача `/uploads/` на старом домене **не настраивается**;
- ссылки вида `https://imagetransformation.ru/uploads/...`, уже отправленные в Telegram и сохранённые в истории, перестанут открываться после отключения старого домена — риск принят владельцем;
- новый код продолжает формировать публичные URL из `WEBAPP_URL` — после смены переменной новые записи сразу получают домен `portret-iz-foto-ai.ru`.

**Смягчение (без доп. работ):** перед шагом отключения старого домена предупредить пользователей в канале/боте о недоступности старых ссылок на результаты.

### Решение 3 (P0). Старые пути страниц на новом основном домене

**Ответ владельца:** 404 сразу — старые пути на новом домене не нужны.

**Зафиксировано:**
- пути `/delovoy-portret-iz-foto`, `/uluchshit-gruppovoe-foto`, `/restavraciya-staryh-foto`, `/raskrasit-cherno-beloe-foto`, `/zhivopisnyy-portret-kak-podarok-na-yubiley` на `portret-iz-foto-ai.ru` **не восстанавливаются и не редиректят** — отдают `404`;

- служебные пути остаются: `/`, `/app/`, `/api/...`, `/uploads/...`, `/oferta`, `/privacy`, `/o-servise`, `/kak-polzovatsya`, `/admin`, `/pay_yookassa`, `/yookassa/webhook`;
- SEO-последствие (потеря позиций старых URL без переноса веса) принято владельцем вместе с решением базового плана об отказе от 301 со старого домена.

### Решение 4 (P1). Политика www

**Ответ владельца:** www НЕ создаём ни для одного домена.

**Зафиксировано:**
- DNS: только A-записи apex для шести доменов (`AAAA` — лишь при реально настроенном IPv6);
- TLS: сертификаты только на apex-имена, `www.*` в SAN не включается;
- Traefik: роутеры только вида `Host(\`<домен>\`)`, middleware `redirect-to-apex` из старого конфига НЕ переносится;
- следствие: запросы к `www.<домен>` завершатся ошибкой DNS/соединения у клиента — принято владельцем;
- развилка в базовом плане (разделы 1 и 4) закрывается выбором «не создаются».

### Решение 5 (P1). Ответ на неизвестный домен

**Ответ владельца:** без catch-all — Traefik сам отвечает дефолтным 404, приложение таких запросов не видит.

**Зафиксировано:**
- в Traefik НЕ создаётся catch-all роутер и middleware-заглушка;
- чекбокс базового плана «неизвестный домен получает 421 Misdirected Request» закрывается средствами Traefik (дефолтный 404) — отдельный код приложения для этого не пишется;
- при этом Fastify всё равно держит явный список известных хостов (для выбора страницы); если запрос каким-то образом дошёл до приложения с чужим Host (например, прямой curl на :8080 из внутренней сети) — отвечать `404` plain text, никогда не отдавать контент лендинга;
- `trustProxy` в Fastify настраивается отдельно (см. соответствующее решение) — на этот выбор не влияет.

### Решение 6 (P1). Локальная отладка и доставка изменений через GitHub

**Ответ владельца:** ngrok не нужен; обязательно — возможность локальной отладки приложения, затем отправка изменений на прод-сервер через GitHub.

**Зафиксировано:**
- ngrok-сценарий выводится из эксплуатации: заголовки `ngrok-skip-browser-warning` из обработчиков `/oferta`, `/privacy`, `/pay_yookassa` в `src/webServer.ts` удаляются при переработке маршрутизации;
- **dev-fallback:** при `Host` = `localhost` | `127.0.0.1` | `[::1]` Fastify отдаёт главную страницу (`site/index.html`) — `yarn dev` работает без спецнастроек;
- проверка host-маршрутизации локально: `curl -H "Host: gruppovoe-foto.ru" http://localhost:8080/` и аналогично для остальных доменов и путей;
- продакшн остаётся за Traefik: снаружи `localhost`-fallback недостижим (Traefik отвечает 404 на неизвестные хосты, см. Решение 5);
- **цепочка поставки:** правки → commit/push в GitHub → на прод-сервере `git pull` → `yarn install && yarn build:all` → `sudo docker compose build bot && sudo docker compose up -d bot` (порядок команд по CLAUDE.md);
- сборка фронтенда обязательна при изменениях `frontend/` (`yarn build:all`, не только `yarn build`).

### Решение 7 (P1). Организация каталогов статики

**Ответ владельца:** вынести HTML в приватный каталог (`content/site/`), в `static/` оставить только публичные ассеты.

**Целевая структура:**
```
content/                    # приватный каталог: НЕ раздаётся @fastify/static
  site/                     # лендинги + инфо-страницы
    index.html
    raskrasit-cherno-beloe-foto.html
    restavraciya-staryh-foto.html
    zhivopisnyy-portret-kak-podarok-na-yubiley.html
    uluchshit-gruppovoe-foto.html
    delovoy-portret-iz-foto.html
    kak-polzovatsya.html
    o-servise.html
  oferta.html
  privacy.html
  pay_yookassa.html
  admin.html
  robots.txt.template       # см. ниже
  sitemap.xml.template      # см. ниже
static/                     # публичные ассеты: раздаются на любом известном домене
  favicon.ico
  site.css                  # (перенос из static/site/site.css)
  <verification-файлы>      # новые файлы Яндекс/Бинг для 6 доменов
uploads/                    # пользовательские файлы (без изменений)
frontend-dist/              # SPA /app/ (без изменений)
```

**Зафиксировано:**
- `@fastify/static` остаётся с корнем `static/` и `wildcard:false` — в корне больше нет HTML, поэтому прямые `/admin.html`, `/pay_yookassa.html`, `/privacy.html` физически исчезают;
- все `reply.sendFile(...)` в `src/webServer.ts` переводятся на пути из `CONTENT_DIR` (`path.resolve(__dirname, "../content")`);
- физические `static/robots.txt` и `static/sitemap.xml` удаляются из раздачи: отдаются явными GET-маршрутами, генерирующими контент по Host (шаблоны — в `content/`);
- проверять `.dockerignore`/Dockerfile: каталог `content/` должен попадать в образ;
- старый `static/site/` упраздняется; ссылка `href="/site/site.css"` в HTML меняется на `/site.css`.

### Решение 8 (P1). Централизация конфигурации доменов

**Ответ владельца:** выбор делегирован агенту («выбери сам как лучше архитектурно»).

**Выбрано: TS-конфиг + подстановка плейсхолдеров при отдаче (вариант 2).**

**Обоснование:** ревизия показала ~40 вхождений адресов в 8 HTML-файлах (canonical, og:url, JSON-LD, CTA). Ручная правка (вариант 1) оставляет дубли и риск рассинхрона; полная шаблонизация (вариант 3) избыточна для статичного сайта. Подстановка при отдаче даёт единственный источник правды без превращения страниц в шаблонный движок.

**Реализация:**
- новый модуль `src/domains.ts` — единственное место со списком доменов:
  ```ts
  export const MAIN_ORIGIN = "https://portret-iz-foto-ai.ru";
  export interface DomainRoute { host: string; landingFile: string; utmSource: string; }
  export const DOMAIN_ROUTES: DomainRoute[] = [ /* 6 записей */ ];
  export const KNOWN_HOSTS = new Set(DOMAIN_ROUTES.map(r => r.host));
  ```
- `WEBAPP_URL` сохраняет имя (переименование в `APP_ORIGIN` не делаем — минимизация churn), но его значение берётся из `.env`, а дефолт меняется на `MAIN_ORIGIN`;
- плейсхолдеры в HTML: `{{SELF_URL}}` (корень текущего хоста: canonical, og:url, JSON-LD), `{{MAIN_ORIGIN}}` (ссылки на юридику/приложение), `{{CTA_APP}}` (готовая ссылка `/app/?example=...&utm_source=<host>&utm_medium=landing`);
- отдача лендинга: чтение файла из `content/` с кэшем сырого содержимого (Map по пути) → замена `\{\{(\w+)\}\}` по значением текущего Host → отправка; подстановка дешевле кэширования готовых страниц по 6 ключам-хостам (второй уровень кэша допустим);
- защита: в dev-режиме assert, что после подстановки не осталось `{{...}}`; в проде неизвестный плейсхолдер заменяется пустой строкой и логируется warning;
- `robots.txt` / `sitemap.xml`: генерируются из шаблонов `content/*.template` тем же механизмом (`{{SELF_URL}}`);
- клавиатуры бота, письма, оферта продолжают использовать `WEBAPP_URL`/`MAIN_ORIGIN` из этого же модуля — дублей в TS не остаётся.

### Решение 9 (P2). Аналитика: удаление всех счётчиков

**Ответ владельца:** удалить все коды всех счётчиков от всех провайдеров.

**Зафиксировано:**
- из всех страниц `content/` удаляется скрипт Яндекс Метрики 111270321 (+ `<noscript>`-часть) — блоки `<!-- Yandex.Metrika counter --> ... <!-- /Yandex.Metrika counter -->`;
- контрольный grep после чистки: отсутствие `mc.yandex.ru`, `metrika`, `googletagmanager`, `gtag`, `analytics` в `content/`;
- раздел 6 базового плана (перенос Метрики, цели, атрибуция `landing_domain`) **не реализуется** — снят с повестки до отдельного решения;
- UTM-разметка CTA (`{{CTA_APP}}` с `utm_source=<host>`) сохраняется — параметры будут работать, когда счётчики вернут;
- важно не перепутать: файлы верификации вебмастеров (Яндекс/Бинг) — это НЕ счётчики, они остаются/создаются для подтверждения владения доменами в Search Console/Вебмастере.

**Последствие принято:** трафик и конверсии не измеряются до повторного внедрения счётчиков.

### Решение 11 (P2). Бэкапы и точка невозврата

**Ответ владельца:** бэкапы не нужны — база маленькая, риск принимается.

**Зафиксировано:**
- `pg_dump` перед миграцией **не выполняется**; копии `.env`/Traefik-конфигов отдельно не создаются;
- бесплатная страховка остаётся из базового плана: перед выкладкой зафиксировать тег предыдущего Docker-образа (`docker images imagetransformationtgbot-ts`) — откат приложения возможен повторным запуском предыдущего образа без пересборки;
- конфиги репозитория защищены git-историей (откат кода = checkout предыдущего коммита);
- **точка невозврата:** удаление A-записей/роутера старого домена (шаг «чистка»). До неё откат возможен возвратом образа + прежнего `.env`; после — только forward-fix;
- владелец осведомлён: без pg_dump любые ошибки при работах с БД на сервере невосстановимы.

### Решение 12 (финальное). Порядок переключения и судьба старого домена

**Ответ владельца:** быстрое переключение за один вечер; деплой и все внешние системы сразу; **старый домен удаляем сразу** — в тот же вечер, без ожидания следующего дня.

**Зафиксировано:**
- **Вечер D0 (одно окно обслуживания):**
  1. DNS новых доменов уже делегированы (проверить заранее днём!); Traefik-роутеры + выпуск TLS;
  2. деплой новой версии: `git pull` → `yarn install && yarn build:all` → `docker compose build bot && docker compose up -d bot`;
  3. немедленное переключение внешних систем: Telegram BotFather (домен WebApp + Menu Button), webhook ЮKassa на новый URL, проверка платежа;
  4. smoke по чеклисту приёмки — письма/оплата/генерация проверяются вживую;
  5. **только при полностью зелёном smoke: удаление старого домена** из Traefik (оба источника конфигурации), A-записей DNS и MX — **точка невозврата проходится этим же вечером**;
- **День D1+:** контроль `docker logs` по ошибкам и платежам; чистка репозитория (grep `imagetransformation.ru`); отправка sitemap в вебмастеров;
- **Предусловия вечера D0:** инвентаризация Traefik (Решение 1) выполнена заранее; домены куплены; ящик почты создан (Решение 10); все правки кода смёржены и локально протестированы (Решение 6).

**Последствие принятого порядка:** между smoke и удалением нет «ночи на раздумье». Если ошибка всплывёт ПОСЛЕ удаления DNS — откат образа приложения возможен, но приём трафика на старый адрес восстановить уже нельзя (Решение 11). Поэтому шаг 5 начинается строго после полностью пройденного чеклиста приёмки, включая живой тестовый платёж и письмо подтверждения.

## Технические заметки

- **trustProxy:** задать адресом/диапазоном шлюза сети Traefik (не `true`!) — иначе webhook ЮKassa может увидеть подменённый `x-forwarded-for`. Текущий код вебхука уже парсит заголовок вручную (`webServer.ts:341–342`) — поведение сохранить.
- **Карта ответов Fastify:** известный Host + назначенный путь → контент; известный Host + чужой служебный путь → 404; неизвестный Host → 404 plain text; localhost → главная (dev).
- **Traefik:** по итогам инвентаризации роутеры добавлять ТОЛЬКО в рабочий источник; правило именования `<домен-через-дефис>`; пример правила: `` Host(`gruppovoe-foto.ru`) `` → service bot:8080.
- **Кэш шаблонов:** сбрасывать не нужно — содержимое меняется только деплоем (новый образ = новый процесс).
